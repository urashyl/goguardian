How This Information Was Obtained

Every claim on this site comes directly from inspecting the GoGuardian Chrome extension and its local browser storage inside an isolated, offline ChromeOS Flex test virtual machine—not from guessing or rumors.

In Plain English: How the Research Worked

1. Local test virtual machine only

All inspection was performed offline on a local ChromeOS Flex virtual machine using the researcher's own test login. No external servers were breached, and no other students' accounts or devices were accessed.

2. Unlocking the local VM disk

Using the account's own password to unlock the virtual machine's encrypted user storage offline, the local Chrome browser profile folder was extracted so its installed extensions and storage files could be read.

3. Reading the installed Chrome extension

Chrome extensions are packaged locally on disk as JavaScript and JSON files (manifest.json, the background service worker, and 22 page scripts). Reading those files reveals exact permissions, monitoring hooks, and server endpoints.

4. Checking local extension storage

Examining the extension's local Chrome database confirmed what gets saved on disk before upload—such as buffered JPEG screenshots and downloaded policy settings. All personal data, credentials, school rules, and proprietary code were removed before publishing.

Stage 1 — User-Space ext4 Extraction

In unprivileged containers where mount -o loop returns EPERM, user-space debugfs inspects the raw ChromeOS Flex stateful partition directly without kernel loop devices.

  • Listed /home/.shadow to locate the profile vault directory /home/.shadow/<user_hash>/.
  • Dumped uss.0 (User Secret Stash ciphertext) and auth_factors/password.gaia (Protobuf KDF metadata) to disk for offline inspection.

Stage 2 — Hardware TPM vs. ChromeOS Flex

Official Chromebooks use dedicated H1/Cr50/Ti50 security chips to seal vault secrets to TPM NVRAM and PCR measurements.

  • Because ChromeOS Flex runs on generic PC hardware without Google security chips, ChromiumOS cryptohome supports multi-factor User Secret Stash (USS) containers.
  • Even when a software TPM (swtpm) NVRAM state is present in a VM, cryptohome stores an independent software-wrapped password.gaia auth factor alongside the vault, allowing offline unwrapping from the account password alone.

Stage 3 — Cryptohome KDF & USS Unwrapping

password.gaia and uss.0 are Protobuf messages encoding salts, scrypt work factors (N=16384, r=8, p=1), ascii_salt_hex, a Wrapped Key Block (wkb_tag, wkb_iv, wkb_ct), and the USS ciphertext (uss_tag, uss_iv, uss_ct). 

h1 = sha256(ascii_salt_hex + password).digest()
passkey = h1[:16].hex().encode("utf-8")
d64 = scrypt(passkey, salt=salt_0, n=16384, r=8, p=1, dklen=64)
derived_key = hkdf_sha256(ikm=d64, salt=b"", info=b"cryptohome USS credential", length=32)
intermediate_key = aes_256_gcm_decrypt(derived_key, wkb_iv, wkb_ct, wkb_tag)
uss_plaintext = aes_256_gcm_decrypt(intermediate_key, uss_iv, uss_ct, uss_tag)

Stage 4 — FlatBuffer & fscrypt v2 Key Verification

The decrypted 352-byte payload is a Google FlatBuffer table (UserSecretStashPayload):

  • Reads the 64-byte File Encryption Key (<FEK>) from FlatBuffer field 0.
  • Derives the Linux kernel fscrypt v2 master key identifier as HKDF-SHA512(IKM=<FEK>, salt=0^64, info="fscrypt\0\1")[0:16].
  • Matching this 16-byte <key_id> against the encrypted directory superblock descriptor on disk verifies cryptographic correctness before touching any file data.

Stage 5 — Offline ext4 & fscrypt v2 Decryption

Without kernel fscryptctl, an offline Python decryptor traverses raw ext4 metadata and extent trees directly:

  • Per-inode xattr: Reads the 40-byte encryption.c extended attribute (version=0x02, AES-256-XTS contents, AES-256-CTS filenames, 16-byte master key ID, 16-byte nonce).
  • Per-inode HKDF: Uses HKDF-SHA512 with <FEK> and each inode's 16-byte nonce to derive a 64-byte file key or 32-byte directory name key.
  • Filenames & Extents: Decrypts filenames via AES-256-CTS-CBC, walks ext4 extent trees (0xf30a leaf extents and interior eh_depth > 0 index nodes), and decrypts 4096-byte blocks with AES-256-XTS using a little-endian block_index tweak.

Stage 6 — LevelDB, Cookies & Extension Analysis

Once the Chrome user profile directory was decrypted, application artifacts confirmed what the extension stores and executes locally:

  • Extension LevelDB: Parsed Local Extension Settings/<extension_id>/ .ldb SSTables (Snappy-compressed blocks) and .log WAL files, recovering buffered Base64 JPEG screenshots (screenshot_<seqId>_dataUrl) and the Base64-wrapped BSON Redux state (store).
  • ChromeOS v10 Cookies: Inspected SQLite cookie storage (encrypted with AES-128-CBC using Chromium's PBKDF2-HMAC-SHA1("peanuts", "saltysalt", 1, 16) key).
  • Extension Static Audit: Analyzed manifest.json, background.js, offscreen-document.js, UI bundles (lock.js, chat.js, checkin.js, presentation.js, video-call.js), and all 22 content scripts (goguardian-1.js–22.js).
